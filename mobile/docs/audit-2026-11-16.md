### 실기기에서만 확인한 추가 사항 (코드 감사 결과에 없거나 보강되는 내용)
- **Capacitor 플러그인 호출 로그**: debuggable 빌드라서 `V/Capacitor`가 모든 플러그인 인자를 찍습니다. 문자 발송 시 `phone`, `text`가 그대로 남습니다. 1-27을 고치면 함께 사라집니다.
- **로그인 화면이 폰클 메인으로 바로 열림**: 서버 세션이 만료된 상태여도 WebView는 `/open/mobile` 껍데기를 띄우고 로그인 폼으로 리다이렉트하지 않습니다(빈 목록). `sawLogin`이 false라서 자동 감지도 동작하지 않습니다. 사용자는 "로그인 완료(자동 감지 안 될 때)"를 눌러야 하는데, 눌렀더니 실제로 세션이 복구됐습니다. 쿠키가 갱신되는 것으로 보입니다. 안내 문구로 이 버튼을 쓰도록 유도하거나, 로드 후 `check()` 프로브로 자동 완료하는 편이 좋습니다.
- **고객 조회에서 이름 검색이 정확히 "100명"을 반환**: "전해성"으로 검색했더니 전혀 다른 고객 100명이 나왔습니다. 폰클 통합검색이 직원명까지 매칭하고 첫 페이지 100건에서 끊기는 것으로 보입니다. 개선 3-12의 '첫 페이지 한계 안내'와, 직원명 매칭 여부를 표시하는 방안을 함께 권합니다.
- **요금제명이 잘려 보임**: `LTE스페셜32990(약정형`, `폰케어 초이스 스`처럼 표시됩니다. 앱의 `cleanPlan`은 자르지 않으므로 `listOpen` 응답 자체가 잘린 것으로 보입니다(미확정). {요금제}를 템플릿에 쓰면 잘린 이름이 문자에 들어갑니다.
- **발송 확인창 문구**: 기본 템플릿의 `{customer}고객님`에 공백이 없어 "…KOZIMJONOVICH고객님"처럼 붙습니다(경미). 문자 길이나 분할(LMS) 표시도 없습니다.
- 정상 동작 확인: 스캔(로그인 후 6명), 조회, 대시보드 수치(재스캔 후 일치), 미방문 탭(514), 이력 탭, 통화(다이얼러 선택창), 백업 파일 공유창, 복원 파일 선택 후 취소, 약정 기간과 템플릿 화면.

> 테스트 중 사고 1건: 백업 공유를 취소한 뒤 뜬 두 번째 공유창에 대시보드를 누르려던 탭이 맞아 "보안 폴더" 잠금 화면이 열렸습니다. 패턴은 입력하지 않고 바로 뒤로 나와 공유된 것은 없습니다. 이 사고 자체가 1-25의 위험성을 보여 줍니다.

## 1. 버그 (확인됨, 심각도순)

### High

**1-1. 백업 복원 뒤 홈의 '발송됨' 표시가 다시 맞춰지지 않음** — `src/main.ts:1152`
- 문제: `restoreFromFile`이 `replaceAll` 다음에 `reconcileSentFlags`, `renderDueList`, `cacheDueList`를 부르지 않습니다. `reconcileSentFlags`는 부팅할 때(1509행)만 실행됩니다.
- 근거: `_verify_40`에서 복원 후 `dedupKeySet().has(id)===true`인데도 `RESULTS[0].already_sent===false`로 실패했습니다.
- 영향: 새 폰에서 스캔한 뒤 복원하면, 이미 안내한 고객이 '알림 보내기'로 남습니다. 다시 누르면 같은 문자가 한 번 더 나갑니다.
- 수정: 복원 직후 `reconcileSentFlags()`, `cacheDueList(RESULTS)`, `renderDueList()`를 호출합니다.

**1-2. 기록 전용(연습) 기록이 '발송됨'으로 집계되고, 배지는 현재 모드를 따라감** — `src/main.ts:221`, `src/domain/history.ts:106`
- 문제: `dedupKeySet()`에 channel 구분이 없어 `record-only`도 `already_sent=true`가 됩니다. 배지 문구는 기록의 channel이 아니라 지금의 `CFG.deliver_alerts`를 봅니다.
- 근거: `_verify_2`에서 record-only 기록을 넣은 뒤 `dedupKeySet().size` 기대값 0이 1로 나왔고, `already_sent` 기대값 false가 true로 나왔습니다.
- 영향: 기본값이 연습 모드라서, 연습 중에 '기록'한 고객은 실제 발송을 켠 뒤에도 '✓ 발송됨'으로 보이고 영영 문자를 받지 못합니다. 조회 화면('안내함 · … 발송')과 미방문 탭도 같습니다.
- 수정: 실제 발송 판정은 `channel==='sms'`만 인정합니다. record-only는 별도 상태로 두고 '실제 발송' 버튼을 보여 줍니다. 배지는 기록의 channel로 정합니다.

**1-3. 테스트 대상이 실존할 수 있는 번호 010-1234-5678로 실제 발송됨** — `src/main.ts:1236` (투표 medium/high)
- 문제: `addTestTarget()`이 고정 번호를 쓰고 `#s-test-phone` 설정값은 쓰지 않습니다. 실제 발송이 켜져 있으면 `doConfirmSend`의 테스트 분기(337-342행)가 그대로 `sendSms`를 호출하고, 이력에도 남지 않습니다.
- 근거: `index.html:72`의 버튼이 릴리스 UI에 항상 보입니다. 네이티브 `normalizeNumber`는 11자리 번호를 그대로 통과시킵니다.
- 영향: 매장 광고 문구 전문이 모르는 사람에게 실제 SMS로 나갈 수 있습니다. 확인 모달에 번호가 표시된다는 점은 위험을 조금 줄입니다.
- 수정: 테스트 행은 `#s-test-phone` 값으로 보내고, 값이 없으면 막습니다. 버튼은 개발 모드에서만 보이게 합니다.

**1-4. 기본 설정(당일만)에서 지나간 마일스톤이 영구히 누락됨** — `src/domain/expiry.ts:167`, `src/domain/keepdate.ts:98` (투표 medium/high)
- 문제: `notify_offsets_days=[0]`이면 `days<0`인 항목은 버려집니다. 미방문 계산은 대표 만료만 보기 때문에 두 경우가 어디에도 다시 나타나지 않습니다. 하나는 약정 대상의 1단계(개통+6개월), 다른 하나는 폰클 유지일(Pass A)입니다.

- 영향: 휴무일이나 주말에 앱을 열지 않으면 해당 고객의 1단계 안내가 경고 없이 사라집니다.
- 수정: 마지막 스캔일 이후 지나간 마일스톤까지 포함해 다시 잡도록 창을 넓히거나, 1단계와 유지일에 대해서도 미방문과 같은 '지난 안내' 목록을 둡니다.

- 영향: 고객은 문자를 받지 못했는데 이력에는 '발송완료'로 남아 이후 스캔에서 빠집니다. 재발송 버튼으로 손으로 복구할 수는 있습니다.

**1-6. 듀얼심에서 '항상 묻기'를 취소해도 '발송완료'로 기록됨** — `android/.../SmsPlugin.java:145`
- 문제: 기본 SMS 구독이 INVALID이면 SIM 선택창이 비동기로 뜨고, `send()`는 바로 반환합니다. 사용자가 취소하면 실패는 null인 sentIntent로만 전달됩니다. API 29~30의 `getDefault()` 경로도 같습니다.

- 영향: 듀얼심 사용자의 발송이 조용히 누락됩니다.
- 수정: `getDefaultSmsSubscriptionId()`가 INVALID이고 SIM이 2개 이상이면 거부하거나, 앱 설정에서 SIM을 고르게 한 뒤 `createForSubscriptionId`를 씁니다.

**1-7. 조회·미방문 탭에서 보내도 홈 목록이 갱신되지 않음** — `src/main.ts:252`

- 근거: 코드 추적. `reconcileSentFlags`를 부르는 곳은 1509행 하나뿐입니다.
- 영향: 홈에 '알림 보내기'가 남아 같은 문자를 두 번 보낼 수 있고, 대시보드의 '미발송 대기' 숫자도 틀립니다.

   - 효과: 1-13, 1-14와 조회 화면의 만료 지난 {when} 문제를 함께 해결합니다.
   - 수정: `daysBetween(expiry, today)`를 쓰고, 음수는 'D+N' 또는 '만료됨'으로 표시합니다. 카드와 whyText도 같은 헬퍼를 씁니다.

   - 효과: 탭이나 키가 어긋나 생기는 중복 발송을 마지막 단계에서 막습니다.
